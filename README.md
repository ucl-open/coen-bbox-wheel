# coen-behaviour-box

Acquisition for the Coen Lab behaviour box: a triggered Spinnaker camera recorded with FFmpeg, frame times paired with Harp triggers, and the Harp board logged raw. Experiment files follow av-dome's (`ActiveExperiments`) layout. The hardware (assembly, parts) lives in [Coen-Lab/hw-behaviour-box](https://github.com/Coen-Lab/hw-behaviour-box).

Generated from the [open-rigs](https://github.com/open-rigs/open-rigs) template (`.copier-answers.yml` records the commit).

## Setup

Needs git, uv and the .NET 8 SDK. From the repository root:

```
scripts\deploy.cmd
```

This creates the Python environment, a starter `rig.yml` from the lab's rig template when the machine has none (keep the box's devices: `behaviorBoard: main`, `camera: overhead`, `videoEncoder`, and fill every CHANGE-ME), downloads the Bonsai version pinned in `.bonsai\Bonsai.config` and restores its packages.

## Per-machine settings

Nothing machine-specific is committed. The workflow reads `<ConfigRoot>\<MACHINE-NAME>\rig.yml` at startup (`ConfigRoot` defaults to `C:\Coen-Lab-Local\RigConfigs`, with the lab's other local files; app-rig-setup moves an older `C:\RigConfigs` there and leaves a link at the old place) and refuses to start if it is missing. `deploy.cmd` creates it from the lab's rig template the first time (keep the box's devices); fill in that machine's board port and the board's USB serial (`usbSerial`: app-rig-control's Hardware page shows each board rig.yml puts on a port beside the board on that port now, and its rig.yml editor saves the file; the rig's hardware summary lists them too, `K:\config\machines\<RIG>\status\<RIG>_RigHardware.json`, `boards`), camera serial number, exposure, gain, binning, wheel size and data path (`rootPath`) there. `videoEncoder` names the camera video's encoder and `ffmpeg.exe` (below, under the camera's files): the template has `codec: h264_qsv`, Quick Sync, as every box is an Intel N150 or N100; left out or `null`, the video is encoded in software (`libx264`) with the first `ffmpeg.exe` on PATH.

`rig.yml` is the source of truth for the hardware: each kind of device is a group of named entries, and each entry binds that name to its port or serial number. The workflow asks for the names it drives, and the name in the data is the kind and the entry joined by a hyphen:

```yaml
behaviorBoard:
  main:              # BehaviorBoard-Main
    portName: COM3
    usbSerial: AB0M7PLB
    ...
camera:
  overhead:            # Camera-Overhead
    serialNumber: '23201539'
    ...
```

The board is found by its port and the camera by its serial number, never by the name. The board on the port must be the one `usbSerial` names (its FTDI chip's serial, which no other board has), or the workflow stops at Start saying which board is where: "COM3 holds the board AQ03WRBO, but rig.yml behaviorBoard: main: (BehaviorBoard-Main) is the board AB0M7PLB, which is not plugged in. ..." (`ExperimentRecords` > `RecordHarpDevices`, OpenRigs.HarpDevices from lib-open-rigs, which reads every Harp device in `rig.yml` itself). A board reporting another device type (WhoAmI) stops it too. An entry the workflow does not ask for (a `spare:` board, say) is ignored. A name it asks for and does not find stops it at Start with the entries the file has: "rig.yml has no camera named 'overhead', which this workflow records as Camera-Overhead. Its camera entries: face. ..." (`RigDevice`, OpenRigs.Core from lib-open-rigs).

## Running an experiment

The workflow runs under an experiment controller (`OpenRigs.Control`, from [Coen-Lab/lib-open-rigs](https://github.com/Coen-Lab/lib-open-rigs), whose README has the protocol; the rig agent and the window that drive it are [Coen-Lab/app-rig-control](https://github.com/Coen-Lab/app-rig-control)): it starts into **ready mode** and records nothing until it is told to go. Pressing Start, or `.bonsai\Bonsai.exe src\main.bonsai --no-editor --property:SubjectId=<id> --property:SessionId=<id>`, connects the board, arms the camera, starts the triggers once it is acquiring and streams the preview (in the editor, the preview and the camera's exposure and gain open on `Hardware` > `Preview`, so they show the camera in ready mode); the first frame reports Ready on the control port (TCP 5561, which answers on this machine only). `SubjectId` and `SessionId` are set in the Properties panel (click an empty part of the workspace) or on the command line; `RunLengthMinutes` (whole minutes, default 30) is a controller parameter, in `Initialization`'s `Parameters`, which the rig agent or `app-rig-control set` may change until Go. Go comes from the rig agent: the window, or `app-rig-control go <rig>`. The agent relays to a workflow it launched and also to one started here by hand, which it shows as unmanaged (commands reach it; nothing is recorded in the lab's records). With no agent running on this machine, send the commands straight to the control port: `app-rig-control go 127.0.0.1 --port 5561`, and `status`, `set` and `stop` the same way. Nothing else starts the experiment: without Go the workflow stays in ready mode. Go reads the IDs and the run length once; the controller refuses Go if either ID is empty or the run length is not a whole number from 1 to 9999 (a `set` outside it is refused too), and nothing is recorded. Otherwise the experiment folder is made (Recording), and after the run length the manifest's run completes (Finished) while the video and CSV go on until the workflow stops; the agent then stops the workflow, which ends it through `ExperimentStoppedException` so every file closes, and waits for Bonsai to exit before recording the experiment. Without the agent, stop it yourself after Finished (the video and CSV run to that Stop). Either way the video writer keeps Bonsai open until `ffmpeg.exe` has closed the file, at most 20 s, and a `.mkv` cut short (Bonsai or `ffmpeg.exe` killed) stays readable up to its last second. In the editor, `--start` needs the machine's editor layout, `.bonsai\Settings\src\main.layout`, which `deploy` creates: without it the editor shows "Object reference not set to an instance of an object." and never starts; pressing Start works either way. Never save the workflow: per-experiment values are set at each run and per-rig values live in `rig.yml`.

The camera's exposure, `Camera-Overhead.ExposureUs` (microseconds), and gain, `Camera-Overhead.GainDb` (dB), are controller parameters beside `RunLengthMinutes`, declared by the `CameraLiveControls` piece with the camera's `Name` as their piece (since 2 Nov 2026; named `CameraExposureUs` and `CameraGainDb` from 9 to 16 Nov 2026; before, Properties-panel overrides). Each starts at the camera's value in `rig.yml`, which the controller shows about a second after Start, and a `set` while ready goes straight to the open camera (`OpenRigs.Video` 0.1.0-bbox.3; bbox.2 dropped every set, as the camera was opened on a copy of the node), so the preview and the camera's readout show the change on the next frame, with no frame lost (tested 2 Nov 2026); Go fixes both, and the manifest records them as they stood at Go. Exposure plus 1,000 us must fit inside the trigger period, so at most 19,000 at 50 Hz: longer, and the camera skips triggers and every frame gets the wrong time, so a longer `set` is refused at the controller with the most that fits (`ParameterMaximum`), and a longer `rig.yml` value stops the workflow at Start (the camera piece's `CameraTrigger` check). Exposure must be at least 100 us and gain 0 to 5 dB (`Maximum`, since 3 Nov 2026: a gain above the camera's own maximum used to be answered ok and then stop the workflow in ready mode with the camera's error). The CSV's `exposureUs` and `gainDb` columns hold what the camera reports for each frame (before 14 Nov 2026, `ExposureTime` held `Camera-Overhead.ExposureUs` at Go). `Binning` is a launch property, the camera piece's (`--property:Binning=2` from the command line): changing it changes the frame size, so the camera takes it only when it opens. Blank, the default, keeps `rig.yml`'s; a value typed in the panel stays for every later Start until you clear it or close Bonsai without saving, and is recorded nowhere but the video's size. The serial number stays in `rig.yml` only: it binds `Camera-Overhead` to the camera.

Each device is a lib-open-rigs piece in `Hardware`, named once as its `Name` (`BehaviorBoard-Main`, `Camera-Overhead`): it takes its entry from `rig.yml`, opens the device behind `<Name>.Data` and `<Name>.Commands`, logs it under `<Name>\` and stops the workflow at Start, naming the entries there are, if `rig.yml` has none by that name ([Building Blocks](https://github.com/Coen-Lab/lib-open-rigs/blob/main/docs/articles/building-blocks.md)). Each half of the name starts with a capital and holds only letters and digits (`Camera-Overhead`, never `Camera-overhead` or `Camera-Overhead_2`: the logging spec reads a device's name up to the first underscore).

A second camera, `Camera-Face` on the board's second trigger, takes these, each by hand: a `face:` entry under `camera:` in every rig's `rig.yml`, named in the `targets` of the board's `CameraTrigger` wiring line; in lib-open-rigs' rig list `BehaviorBoxHardware` (which `Hardware` includes, as does the box's preflight), a second `SpinnakerCamera` piece named `Camera-Face`, added to its `CameraTriggers`' `CamerasExpected` and its `ReadyGate`'s `PieceStages`, so every box has it. `workflow_lint.hardware_problems` (pytest) names anything missed.

Two windows open at Start, from ready mode on: the camera preview, 5 frames a second (`Hardware` > `Preview`), and below it the exposure and gain the camera reports for its frames, read back from the camera rather than the values asked for (`Hardware` > `Preview` > `CameraSettings`, "Exposure 2999 us   Gain 1.00 dB"). They are the workflow's layout, `config\main.layout`, which `.bonsai\Setup.ps1` (lib-open-rigs' `setup-bonsai.ps1`, run by `scripts\deploy.ps1` and by app-rig-setup when the layout changes) copies to the machine's `.bonsai\Settings\src\main.layout` every time it runs, keeping a different one as `main.saved.layout`. If a window is closed or missing, double-click its node while running. The layout names nodes by their position in the group as Bonsai loads it, which is topological order, not the file's: a node that feeds one above it in the file moves up, so add nodes at the end of their group, and `scripts\check-workflow.ps1` checks each window is on a node it fits. A window on the wrong node makes the editor ask whether to delete the layout file, and an editor started by the rig agent waits on that question: answer No, and fix `config\main.layout`. Close Bonsai without saving: a save writes the run's values into `main.bonsai` and the windows open at the time into the layout.

If no frame arrives for 15 s, the workflow stops with "Camera-Overhead: no frame for 15 s after the camera trigger started, so the run was stopped. ..." (the camera piece's watchdog; usually the trigger cable).

## Layout

The workflow's top level follows the open-rigs layout: `ReadLabRig` (this machine's `rig.yml`, lib-open-rigs' lab rig model), `Initialization` (the run settings), `LogLabExperiment` (the experiment folder at Go, `BonsaiData_Async`, the settings files; before `Hardware`, as every device's log waits for its folder), `Hardware` (the Ready gate, the board, its clock, the wheel, the camera and its trigger, the camera's live exposure and gain, the editor's preview), `TaskLogic` (the run length's frames, then Finished), `ExperimentRecords` (lib-open-rigs' shared records, as the dome tasks': the controller's events, the board's record and the manifest) and `LiveView` (streams every device; below).

## Data

Each experiment writes to `<rootPath>\sub-<subject>\ses-<session>_<date>\` (ucl-open/roadmap#37; `ses-<session>_date-<date>` before 2 Nov 2026), one folder per device named as the device, and each device's files as `<Device>_<DateTime>` in one-hour chunks on the board's Harp clock, as the Open Rigs logging spec (`ucl-open/specs/logging.md`) has it. The workflow sets that clock to the PC's UTC time when the board connects (`Hardware` > `ClockFromBoard`, whole seconds, so up to 1 s behind the PC), and logs nothing from the board until it has. The clock counts as set once a TimestampSeconds message from the board is within 2 s of the PC's UTC time (OpenRigs.Devices `HarpClockSet`, published as `HarpClockSet` by lib-open-rigs' `ClockFromBoard` piece; the dome tasks' `DomeHardware` publishes it from the timestamp generator); until then each of the board's once-a-second heartbeats sends the write again. If it is not set 10 s after Start, the workflow stops with "Setting the board's clock to UTC (...) did not finish within 10 s. Arrived: nothing. Never arrived: HarpClockSet." (OpenRigs.Core `StartupWatchdog`; its messages are not reaching the PC, or the board is not responding) rather than record a whole experiment without the board's files. So `<DateTime>`, and `harpTime` in the CSV, are UTC: chunks start on the clock hour, not an hour into the run. `<DateTime>` is the chunk's start, so a run crossing the hour has two of each file:

- `Camera-Overhead\Camera-Overhead_<DateTime>.mkv`: H.264 video (Matroska) of every frame received, written by `OpenRigs.Logging:LogVideoFfmpeg` (lib-open-rigs `docs\bonsai-operators\OpenRigs.Logging\log-video-ffmpeg.md`), as the dome tasks' cameras are, through `ffmpeg.exe` with `rig.yml`'s `videoEncoder`. A frame the camera drops is missing, not repeated, and the recording runs from the camera's first frame until the workflow stops, so it is longer than the run length (the manifest's run completes at the run length's frames: 30 min at 50 Hz = 90,000). A frame the writer has to drop (its queue of 250 full) stops the run with an error, or at a Stop leaves `Camera-Overhead_<DateTime>.error.txt` beside the video.
- `Camera-Overhead\Camera-Overhead_<DateTime>.csv`: one row per video frame, row `n` frame `n` of the video, the dome tasks' columns: `harpTime` (the Harp time of its trigger, in seconds), `frameId` (the camera's frame counter), `cameraClockNs` (the camera's own clock at the exposure, ns), and `exposureUs` and `gainDb` as the camera reports them for that frame (3000 asked for can read 2999). A dropped frame shows as a jump in `frameId` and `harpTime`. Trigger messages lost between the board and the PC do not show in `frameId`: frames pair with trigger messages in order (a dropped frame holds its trigger's place), so from the first lost one every later row's `harpTime` is late by the number lost (seen once, 30 Oct 2026: 9 lost, every later row 0.18 s late; BACKLOG, "Lost board messages"). The sign is a step in `harpTime` other than the trigger period (20 ms at 50 Hz) where the step in `cameraClockNs` is one period; `cameraClockNs` is the camera's own clock, so `harpTime` can be rebuilt from the rows before the first such step. `check-videos <experiment folder>` (lib-open-rigs) counts each video's decoded frames against its CSV.
- `BehaviorBoard-Main\BehaviorBoard-Main_<address>_<DateTime>.bin`: every Harp event and write from the board, one file per register, logged with `OpenRigs.Logging:LogHarpDevice` (the same logger as ucl-open main). The running wheel's raw encoder position is in `BehaviorBoard-Main_44_*` (`AnalogData`, `Encoder`) at the board's full rate, about 1 kHz.
- `BehaviorBoard-Main\BehaviorBoard-Main_<DateTime>.bin`: the board's register dump (its read replies, one file for every register), which `RecordHarpDevices` asks for 0.5 s after the experiment folder appears, so its settings for the experiment are on record. (av-dome's current logger, `UclOpen.Logging` from May 2026, keeps only the first reply of each second: ucl-open/av-dome#33.)
- `BehaviorBoard-Main\BehaviorBoard-Main_device.json`: which board it was: its port, USB serial, WhoAmI, hardware, firmware and core versions, device name and Harp serial, from that dump once it has finished (`RecordHarpDevices`).
- `BehaviorBoard-Main\BehaviorBoard-Main.yml`: the board's register map, Harp.Behavior's `device.yml`, so the `.bin` files can be decoded from the experiment alone.
- `BonsaiData\BonsaiData_Async_<DateTime>.csv`: the controller's events (Go, Stop, phase changes, parameter sets), written by `ExperimentRecords` (`LogControlEvents`) as the dome tasks write theirs.
- `Settings\Settings_Rig_<DateTime>.json`: `rig.yml` as parsed, written with OpenRigs.Logging's `LogDataSchema` as the dome tasks write theirs (so is `Settings_Experiment`). The file is complete once the workflow has stopped (`LogDataSchema` closes it then; a Bonsai killed outright leaves it empty); `SessionJson`, the workflow's own writer until 15 Nov 2026, wrote it at once.
- `Settings\Settings_Experiment_<DateTime>.json`: the experiment's settings at Go, from OpenRigs.Control's `ExperimentSettings`: subject, session, rig, workflow, repository, commit, who launched and sent Go, and every ExperimentControl parameter at Go (`RunLengthMinutes`, `Camera-Overhead.ExposureUs`, `Camera-Overhead.GainDb`; `CameraExposureUs` and `CameraGainDb` from 9 to 16 Nov 2026; `RunLengthMins`, `ExposureTime`, `Gain` before). Before `dc212a6` (6 Nov 2026) the rig file was `RigSchema\RigSchema_<DateTime>.json` and the parameters were in `manifest.json`'s `control`; from `dc212a6` until `1a8f95d`, later the same day, both files were in `Schemas\` (`Schemas_Rig_<DateTime>.json`, `Schemas_Experiment_<DateTime>.json`).

Earlier experiments have `Camera-Box\Camera-Box_<DateTime>.avi` (`Camera-Overhead\` after the rename of 14 Nov 2026) and a CSV of `Seconds`, `Timestamp`, `FrameID` and `ExposureTime` (`CameraExposureUs` at Go). Experiments before 30 Oct 2026 have `Cameras\VideoData_Camera1.avi` and `.csv`, one file per run, and `BehaviorBoard\BehaviorBoard_*`. Before the clock was set (30 Oct 2026), the board counted from power-on, so file names read `1904-01-...` and Harp times are uptime, not UTC.

## Experiment manifest

Every experiment folder gets a `manifest.json` (`ExperimentRecords` > `ExperimentManifest`, the OpenRigs.Manifest package from lib-open-rigs; format: its [`FORMAT.md`](https://github.com/Coen-Lab/lib-open-rigs/blob/main/src/OpenRigs.Manifest/FORMAT.md), version 3). It finds the experiment folder (`PathPrefix`) itself and takes no input, as the dome tasks' (since 16 Nov 2026; before, the frames recorded were its input and `run.items` their count, now null: the camera CSV's rows count them). It is written when the experiment folder exists and again when the run ends:
- the machine, the subject and session from the folder name;
- this repo's commit and whether the clone was dirty;
- Bonsai's command line with each `--property` value;
- the subject, session and who launched it and sent Go, from the experiment controller (the parameters at Go are in `Settings_Experiment`);
- `rig.yml` as read at Start, with its sha256;
- how the run ended: `completed` when the run length's frames were written (`TaskLogic` reports Finished), `error` with a Watchdog's message, `stopped` after a controller stop (with its reason), `ended-early` when the workflow stopped any other way;
- `expected`: a folder for each device in `rig.yml` this workflow publishes (`BehaviorBoard-Main/`, `Camera-Overhead/`), each Harp device's `_device.json` and `.yml` (`harp`), and `Settings/Settings_Rig_` and `Settings/Settings_Experiment_`, each settings file on its own, with how many files each holds;
- every file in the folder with its size. The workflow is the manifest's only writer: the overnight copy (jacuzzi-ingest's `ingest-rig`) checks every listed file is present and closed, hashes each into its own `sync.json`, and only then copies the experiment to the server, `manifest.json` and then `sync.json` last. For a `completed` run, a listed file that is missing, or an expected folder holding nothing (a board that never logged), stops that experiment's copy and raises an alarm in the rig's sync record; a run that did not complete is copied with the gap noted and an alarm. `ingest_script` is `coen-behaviour-box`, the name the server's ingest registry runs for this data. Errors on the board's logging chain do not reach the node, so an experiment whose board log failed reads `ended-early`, not `error`; its empty `BehaviorBoard-Main/` is what says so.

## Live view

While it runs, the workflow streams over ZeroMQ for app-rig-control's window: data on TCP 5556, video on 5558, bound on every interface (app-rig-setup's `firewall:live-view` opens both to the local subnet). One node does it, `LiveView`, OpenRigs.LiveView's `StreamDevices` (from [Coen-Lab/lib-open-rigs](https://github.com/Coen-Lab/lib-open-rigs)), last in the workflow: it reads this machine's `rig.yml` when the workflow is built and streams each device there whose data the workflow publishes as `<Kind>-<Instance>.Data`, so the board's events are `BehaviorBoard-Main.Data` and the camera's frames `Camera-Overhead.Data`, and a device added under that convention is streamed without touching `LiveView`. Each message is a topic `<MACHINE-NAME>/<stream>/`, a JSON header (`rigId`, `sessionKey`, `stream`, `index`, `enc`, `type`) and the payload. The session key is `ready` until the experiment folder exists, then the folder's own name, `sub-<subject>/ses-<session>_<start>`. Streams:

- `Camera-Overhead.video`: the camera's frames from Start (in ready mode too), 5 a second, 320 x 240 JPEG.
- `BehaviorBoard-Main.encoder`: the raw encoder count (`AnalogData.Encoder`, 16-bit, wrapping), 10 times a second.
- `elapsed`: seconds since the experiment folder appeared, once a second.
- `liveview`: every 5 s, this workflow (its path, commit and whether the clone was dirty, as `manifest.json` records them) and the devices streamed and skipped, and why.

A device's rate, and a camera's frame size, can be changed in `rig.yml` under the device's `liveView:` (`rate`, `width`, `height`, or `enabled: false`); the template has `liveView: null`, the defaults. `--property:ConfigRoot` reaches `ReadLabRig` (which publishes it to the camera's video writer), and `ExperimentRecords` (`RecordHarpDevices`), one workflow property mapped to both; `LiveView` keeps its own, the lab's, since an edge into it makes Bonsai build it before the devices and it would stream nothing (`scripts\check-workflow.ps1` redirects every node's); `ExperimentManifest` records `rig.yml` under it and every file it names (`{RigFiles}`).

Viewing never reaches the recording: a subscriber that is slow or joins late loses its own messages (the header's `index` shows the gap), and with none connected the messages are dropped. Another workflow already streaming on these ports stops this one at Start (`AddressAlreadyInUseException`); Stop and Start again in the same window is fine (tested with Start 0.7 s after Stop): the new run's messages carry its own session key, and each stream's `index` starts again at 0. app-rig-control shows the stream.

## Checks

```
powershell -NoProfile -ExecutionPolicy Bypass -File scripts\check-workflow.ps1
```

On a deployed clone, with no Bonsai window and no hardware: lib-open-rigs' `check-workflow.ps1` (one copy for every lab workflow, from the open-rigs this repo pins) compiles `src\Extensions` as C# 5, builds `src\main.bonsai` with Bonsai's own builders against the lab's rig template filled in with exactly this workflow's devices, checks the board's record and dump request, the manifest's device folders and Harp records, the tracked layout's windows on their nodes, and that `Settings_Rig` keeps every key of the template. Exit 0 when all pass. It cannot check the camera, the board or the hour hand-over: those need the rig (`BACKLOG.md`, "Check on the rig").

`uv run pytest -q` holds `src\main.bonsai` to the lab's rules (open-rigs' `workflow_lint`: the pieces and their order, Ready, the experiment logs, every file written in `ExpectedFiles`, the commands, the tracked layout). app-rig-setup's `update-workflows.ps1` runs it after `check-workflow.ps1`.

## OpenRigs packages

Every package in `local_packages\` comes from [lib-open-rigs](https://github.com/Coen-Lab/lib-open-rigs), which holds one version of each for all the lab's workflows: the lab's own (`OpenRigs.Control`, `OpenRigs.LiveView`) and patched builds of open-rigs' `OpenRigs.*` packages, until upstream releases the fixes (its `patches\README.md` has base commits, patches and hashes). app-rig-setup's `workflows\update-workflows.ps1` replaces the copies here when a package there changes, pins open-rigs (Python, `pyproject.toml` and `uv.lock`) to the same commit, runs `scripts\check-workflow.ps1`, and commits and pushes only if the check passes. Do not change a package here by hand: change it there.
